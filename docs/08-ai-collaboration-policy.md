# 08 — AI Collaboration Policy

## Document Purpose

This document defines the artificial intelligence collaboration policy for KUNNA.

The policy was initially established during the **I1 — Inception Package** and remains active during **I2 — Elaboration** and subsequent project work.

The purpose of this policy is to establish how AI-assisted tools may support the project without replacing human understanding, professional judgment, authorship, verification, or responsibility.

This policy applies to:

- Product discovery.
- Requirements analysis.
- Use case modeling.
- Supplementary requirements.
- Risk analysis.
- Domain modeling.
- UML modeling.
- Object-oriented analysis and design.
- Architecture decisions.
- Java implementation.
- Testing.
- Technical documentation.
- Git and GitHub workflows.
- Research support.
- Portfolio preparation.

## Project Context

KUNNA is a personal software engineering project based on an original UX/UI prototype.

The project has two complementary purposes:

1. Evolve KUNNA as a maintainable software product through disciplined engineering.
2. Demonstrate the project owner's software engineering learning and professional development through credible evidence.

The portfolio purpose must not determine product requirements, architecture, technology choices, or implementation scope.

Artificial intelligence may support this process, but it must not obscure who made the decisions, how conclusions were reached, what evidence exists, or whether the project owner understands the resulting artifacts.

## Core Principle

AI is a support tool, not the owner, author, decision-maker, or accountable party for the project.

The project owner remains responsible for:

- Defining the problem.
- Understanding the domain.
- Selecting the project direction.
- Evaluating alternatives.
- Approving requirements.
- Validating models.
- Reviewing generated content.
- Writing or accepting implementation decisions.
- Verifying code behavior.
- Protecting sensitive information.
- Explaining every relevant project artifact and technical decision.

No AI-generated output is accepted automatically.

## Human Accountability

The project owner has final responsibility for every artifact committed to the repository.

Before accepting AI-assisted content, the project owner must be able to:

- Explain its purpose.
- Explain its main concepts.
- Identify its relationship with previous artifacts.
- Justify why it belongs in the project.
- Detect obvious inconsistencies.
- Modify it when necessary.
- Describe its limitations.
- Defend the resulting decision in an academic, technical, or professional conversation.

Content that cannot be explained by the project owner should not be merged into `main`.

## Permitted Uses of AI

AI tools may be used to support the following activities.

### Learning Support

AI may help:

- Explain software engineering concepts.
- Compare approaches and terminology.
- Clarify Git and GitHub workflows.
- Provide examples for educational purposes.
- Translate technical ideas between English and Spanish.
- Generate questions for self-evaluation.
- Identify knowledge gaps that require additional study.

AI explanations must be treated as learning support and not as unquestionable authority.

### Documentation Support

AI may help:

- Propose document structures.
- Improve clarity and consistency.
- Detect duplicated or ambiguous wording.
- Review grammar and Markdown formatting.
- Suggest acceptance criteria.
- Summarize decisions already made by the project owner.
- Connect related project artifacts.
- Generate an initial draft for human review.

The final document must reflect the actual KUNNA project rather than generic AI-generated content.

AI must not create documentation merely to make the repository appear more complete.

### Requirements Support

AI may help:

- Identify candidate user goals.
- Suggest candidate actors.
- Detect possible ambiguities.
- Review use case consistency.
- Suggest candidate functional and non-functional requirements.
- Identify missing assumptions or open questions.
- Check traceability between vision, goals, use cases, requirements, and risks.

AI must not invent validated user needs, research findings, stakeholder opinions, legal obligations, or product evidence.

Candidate requirements generated by AI remain hypotheses until reviewed and accepted by the project owner.

### Modeling and Design Support

AI may help:

- Explain UML notation.
- Suggest candidate domain concepts.
- Review model consistency.
- Compare design alternatives.
- Explain object-oriented principles.
- Suggest GRASP or other design patterns for evaluation.
- Detect possible responsibility or coupling problems.
- Assist in documenting architecture decisions.

AI suggestions do not replace analysis.

Architecture patterns, design patterns, frameworks, or abstractions must not be selected only because they are common, popular, or suggested by an AI system.

Domain concepts, UML elements, or analysis classes must not be converted mechanically into implementation classes.

The project owner must determine whether a model or design decision is appropriate for KUNNA and whether current evidence justifies it.

### Implementation Support

AI may help:

- Explain Java language features.
- Generate small code examples.
- Suggest refactorings.
- Review naming and organization.
- Identify possible defects.
- Suggest tests.
- Explain compiler or runtime errors.
- Explain frameworks, libraries, APIs, or infrastructure when a demonstrated project need makes them relevant.

Generated code must not be committed without:

- Human review.
- Understanding of its behavior.
- Appropriate modification when necessary.
- Testing.
- Verification against relevant project requirements.
- Verification against current architecture decisions.
- Consideration of security and maintainability.
- Review of introduced dependencies.

When AI suggests a dependency, library, framework, or external service, the project owner should verify, when relevant:

- Why it is needed.
- Whether the same problem can be solved with less complexity.
- Source and official documentation.
- License.
- Maintenance status.
- Compatibility.
- Security implications.
- Operational consequences.

Passing compilation alone is not sufficient evidence for accepting generated code.

### Testing Support

AI may help:

- Suggest test scenarios.
- Derive candidate tests from acceptance criteria.
- Identify edge cases.
- Explain testing strategies.
- Review test coverage conceptually.
- Suggest test data that does not contain real personal information.

Passing AI-generated tests does not prove that the software is correct.

The project owner must validate whether the tests represent the intended behavior and whether the implementation satisfies the relevant requirement or acceptance criterion rather than merely satisfying the generated test.

### Workflow Support

AI may help:

- Draft branch names.
- Propose Conventional Commit messages.
- Draft issue or pull request descriptions.
- Review acceptance criteria.
- Explain merge conflicts.
- Suggest Git commands.
- Help interpret Git output.

Commands must be reviewed before execution.

Destructive commands must not be executed unless their effect is understood.

## Prohibited Uses

AI must not be used to:

- Replace the project owner's learning process.
- Generate work that the project owner cannot explain.
- Fabricate research, interviews, tests, citations, or evidence.
- Invent stakeholder validation.
- Present unverified claims as facts.
- Present hypotheses as validated requirements.
- Make autonomous product decisions.
- Select architecture or technologies solely because they are commonly used or recommended by AI.
- Make final legal, health, safety, or child-protection judgments.
- Process confidential information without authorization.
- Receive passwords, credentials, tokens, or private keys.
- Receive real personal information about children, families, or caregivers.
- Generate deceptive commit history or authorship claims.
- Hide the use of AI when disclosure is relevant.
- Copy protected material without respecting applicable rights.
- Introduce dependencies or code that have not been reviewed.
- Merge generated content directly into `main` without human validation.

## Sensitive Domain Considerations

KUNNA concerns families, caregivers, children, positive parenting, and children's rights.

This domain requires additional caution.

AI-generated content related to the following areas must be treated as unverified until reviewed against reliable and appropriate sources:

- Children's rights.
- Colombian laws and regulations.
- Child protection.
- Parenting recommendations.
- Psychological guidance.
- Health information.
- Safety recommendations.
- Educational guidance.
- Institutional procedures.

For sensitive domain content, source provenance should remain traceable when that content influences a requirement, product decision, recommendation, or user-facing statement.

Relevant verification may include:

- Original source.
- Responsible institution or author.
- Publication or update date when relevant.
- Applicable jurisdiction.
- Scope and limitations.
- Whether the information remains current.
- Whether multiple authoritative sources disagree.

AI must not be presented to future KUNNA users as a substitute for:

- Qualified legal professionals.
- Health professionals.
- Mental health professionals.
- Child-protection authorities.
- Emergency services.
- Official government institutions.

## Privacy and Data Protection

No real sensitive personal information should be entered into AI tools during the development of KUNNA.

This includes:

- Full names of children.
- Identification numbers.
- Addresses.
- Telephone numbers.
- Email addresses.
- Health information.
- Family conflicts.
- Legal cases.
- School records.
- Psychological information.
- Photographs containing identifiable minors.
- Authentication credentials.
- Private repository secrets.
- API keys or access tokens.

Examples and test data should use fictitious, anonymized, or synthetic information.

The minimum necessary information should be shared with any external tool.

## Verification Policy

AI-assisted output must be verified according to the type of work.

### Documentation Verification

Check:

- Consistency with existing artifacts.
- Correct terminology.
- Project-specific relevance.
- Absence of unsupported claims.
- Clear relationship with KUNNA's product vision and current project phase.
- Correct Markdown formatting.

### Requirements Verification

Check:

- Alignment with user goals.
- Traceability to product vision, research, or explicitly identified hypotheses.
- Testability.
- Lack of contradictions.
- Clear scope.
- Whether the requirement is validated or only a hypothesis.
- Whether implementation feedback requires the requirement to be refined.

### Modeling Verification

Check:

- Correct domain meaning.
- Consistent actor and use case definitions.
- Correct UML semantics when UML is used.
- Appropriate abstraction level.
- Absence of unnecessary implementation details in conceptual models.
- Traceability with requirements.
- Whether the model is focused on the current analysis need.
- Whether implementation evidence challenges an earlier model assumption.

### Architecture and Design Verification

Check:

- Which risk or uncertainty the proposal addresses.
- Which requirement or quality concern motivates it.
- What assumptions it introduces.
- What alternatives were considered.
- Whether the decision can be tested or otherwise validated.
- Whether the proposed complexity is justified.
- Whether a dedicated ADR is warranted.

An AI-generated architecture description is not architectural evidence by itself.

### Code Verification

Check:

- Compilation.
- Automated tests.
- Expected behavior.
- Error handling.
- Security implications.
- Dependency impact.
- Readability.
- Maintainability.
- Consistency with current architecture decisions.
- Compliance with relevant project requirements.
- Traceability to the behavior being implemented.

Code and tests should be evaluated together against the intended behavior rather than accepted merely because they agree with each other.

### Research Verification

Check:

- Source existence.
- Source quality.
- Publication date when relevant.
- Author or institution.
- Context.
- Jurisdiction when relevant.
- Possible conflicts between sources.
- Whether the conclusion is actually supported by the cited evidence.

AI-generated citations or references must never be accepted without confirming that the source actually exists and supports the stated claim.

## Traceability of AI-Assisted Work

AI collaboration should remain traceable without creating unnecessary administrative overhead.

Relevant AI assistance may be documented through:

- Pull request summaries.
- Decision journal entries.
- Architecture Decision Records.
- Notes inside project artifacts when justified.
- Issue discussions.
- Source references.
- Verification evidence.

Not every minor spelling correction requires explicit AI disclosure.

Disclosure becomes important when AI meaningfully influences:

- Requirements.
- Product decisions.
- Architecture.
- Domain models.
- UML models.
- Algorithms.
- Security decisions.
- Legal or safety-related content.
- Large portions of documentation or code.

Traceability should explain meaningful influence without attempting to record every individual AI interaction.

## Git and GitHub Rules

AI-assisted work follows the same professional GitHub workflow as all other project work.

The current Project board states are:

```text
Backlog → Ready → In Progress → Review → Done
```

Detailed execution rules are maintained in:

- `docs/06-development-plan.md`
- `docs/07-development-framework.md`

AI must not bypass issue traceability, local validation, pull request review, acceptance criteria, or final human approval.

Git commands suggested by AI remain the responsibility of the person executing them.

## Decision-Making Rule

When AI proposes a solution, the project owner should evaluate:

1. What problem does this solve?
2. Is the proposal consistent with KUNNA's vision and current scope?
3. What evidence supports it?
4. What assumptions does it make?
5. What alternatives exist?
6. What risks does it introduce or reduce?
7. Can the project owner explain it?
8. Can the result be verified?
9. Is the level of complexity justified?
10. Should the decision be documented?

If these questions cannot be answered, the proposal should remain unaccepted.

## AI-Assisted Content Status

AI-generated material may have one of the following states:

| Status       | Meaning                                                         |
| ------------ | --------------------------------------------------------------- |
| Candidate    | Initial suggestion that has not been reviewed                   |
| Under Review | Content currently being evaluated                               |
| Accepted     | Content reviewed, understood, and approved by the project owner |
| Modified     | AI-assisted content substantially adapted by the project owner  |
| Rejected     | Content considered unsuitable for KUNNA                         |
| Superseded   | Previously accepted content replaced by a better decision       |

Only accepted or modified content should become part of the project's authoritative artifacts.

These labels are conceptual review states and do not require a separate administrative record for every AI-assisted change.

## Examples for KUNNA

### Acceptable Example

AI suggests possible use cases based on documented user goals.

The project owner reviews the suggestions, removes unsupported cases, adjusts terminology, connects the remaining cases to the product vision, and documents the accepted model.

### Unacceptable Example

AI generates a complete use case model and it is committed without reviewing the actors, goals, scope, assumptions, or consistency with KUNNA.

### Acceptable Example

AI proposes Java tests for behavior associated with a selected use case.

The project owner verifies the relevant requirements or acceptance criteria, reviews each test, adjusts the expected behavior, runs the test suite, and explains the implementation.

### Unacceptable Example

AI generates production code that is merged because it compiles, even though the project owner cannot explain its architecture, dependencies, or security implications.

### Acceptable Example

AI helps summarize official information about children's rights after the project owner verifies the original sources and preserves appropriate provenance.

### Unacceptable Example

AI-generated legal or child-protection statements are published in KUNNA without verification from authoritative sources.

## Authorship and Portfolio Integrity

The KUNNA repository represents the project owner's professional development.

AI assistance must strengthen, not weaken, the credibility of the portfolio.

The project owner should be prepared to explain:

- Why each artifact exists.
- How it was created.
- What role AI played.
- What was reviewed or changed.
- Which decisions were made independently.
- What was learned during the process.
- What limitations remain.

The portfolio must not imply expertise, research, implementation, or validation that did not occur.

Product requirements, architecture, technologies, or artifacts must not be added merely to make the portfolio appear more sophisticated.

## Review and Evolution

This policy is a living artifact.

It should be reviewed when:

- New AI tools are introduced.
- AI meaningfully influences implementation or architecture.
- Sensitive data becomes relevant.
- External collaborators join.
- The architecture changes materially.
- AI-generated code becomes more frequent.
- New legal, academic, or organizational requirements apply.
- External APIs, AI services, or other third-party services are considered.
- Verification practices prove insufficient.

Changes to this policy should follow the normal GitHub workflow.

## Acceptance Criteria

This policy remains effective when:

- Permitted AI uses are documented.
- Prohibited AI uses are documented.
- Human responsibility is explicit.
- Verification requirements are defined.
- Privacy and sensitive-domain safeguards are included.
- Research and source provenance expectations are clear.
- Architecture, code, tests, and dependencies require independent human validation.
- Git and GitHub traceability expectations remain aligned with the project's current workflow.
- Portfolio integrity is protected.
- The project owner can explain and apply the policy.

## Portfolio Value

This policy demonstrates:

- Responsible use of AI.
- Human accountability.
- Verification discipline.
- Privacy awareness.
- Ethical software engineering.
- Requirements traceability.
- Evidence-based architecture and implementation decisions.
- Professional GitHub workflow.
- Awareness of sensitive product domains.
- Ability to distinguish assistance from authorship.
- Ability to use AI without surrendering technical judgment.

## Current Policy Position

The AI collaboration policy was established during I1 and remains active during **I2 — Elaboration**.

During I2, particular attention applies to:

- Distinguishing hypotheses from validated requirements.
- Preserving traceability between analysis, architecture, implementation, tests, and evidence.
- Preventing AI suggestions from determining architecture or technology adoption without demonstrated need.
- Independently validating generated Java code and automated tests.
- Verifying dependencies and external services before adoption.
- Preserving reliable source provenance for sensitive domain content.

The policy should continue evolving only when project evidence or new risks justify a change.
